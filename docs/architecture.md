# Architecture

## Current implementation boundary

Orbyt owns project/task organization, source selection, triage workflow, persistent execution lifecycle, and scheduling. OpenCode owns AI reasoning, tool execution, and agent session behavior. The app provides persisted project/task workflows, GitHub App Device Flow, Project/Status-based Issue intake, linked GLPI 10 context, stateless triage, and supervised ACP runs. Local tasks require explicit approval; sufficiently contextual tasks from a configured GitHub Project can start automatically in its selected writable scope.

## Runtime structure

- `src/`: React 19 + TypeScript strict-mode desktop presentation.
- `src/App.tsx`: route-level screens and user workflows, backed by TanStack Query.
- `src/lib/commands.ts`: typed Tauri invocation boundary; UI does not access SQLite or spawn processes.
- `src-tauri/src/execution.rs`: persistent execution commands, transactional scheduler/locks, and the private OpenCode ACP process lifecycle.
- `src-tauri/src/integrations/github_app.rs`: GitHub App Device Flow, OS-keyring token refresh, ProjectV2/field discovery, and read-only assigned Issue filtering.
- `src-tauri/src/integrations/glpi_ticket.rs`: GLPI 10 ticket context, public follow-up history, attachment metadata/download, and reviewed public follow-up creation.
- `list_opencode_sessions`: read-only session metadata discovery through the installed OpenCode CLI, scoped to registered canonical project directories.
- `triage_task`: sends Issue text and linked GLPI ticket text/public follow-ups/attachment metadata to OpenCode's stateless text generation operation; it does not read project files or attachment bytes, use tools, or create a session. A sufficiently contextual GitHub Project task with its configured scope is queued for ACP after the report is saved.
- `get_task_triage`: returns the saved report only when its task content revision still matches.
- `queue_task_execution`, `list_task_runs`, `respond_to_run_permission`, `cancel_task_run`, and `reconcile_task_run`: typed commands for manually approved local runs and authorized auto-started GitHub Project runs; they never accept arbitrary commands from the UI.
- `src/lib/task-rules.ts`: frontend transition reference; authoritative validation is in Rust.
- `src-tauri/src/domain.rs`: domain validation and task state transition rules.
- `src-tauri/src/lib.rs`: SQLite repository operations and thin validated Tauri command entrypoints. The database is initialized in app-local data and accessed behind a mutex.
- `src-tauri/migrations/`: ordered SQL migrations; the applied migration versions are persisted in `schema_migrations`.
- `src-tauri/capabilities/`: Tauri v2 capability allowlist. The UI has the native directory chooser and the narrowly registered application commands; no shell plugin is exposed.

Rust owns persistence and privileged interactions. Project removal cascades Orbyt records but never acts on filesystem content. Project registration canonicalizes and checks existing directories, and rejects canonical paths that cannot be represented as Unicode before persistence. Scope creation resolves the target canonically, requires it to remain under the project root, and rejects traversal and symlink escapes. Scope definitions express intended read/write areas; they do not claim kernel-enforced isolation.

## Persistence and domain

The SQLite schema stores projects, execution scopes, tasks, settings, GitHub Project source configuration, task transition history, triage reports, task runs, scope locks, and ACP permission decisions. Ordered migrations are recorded in `schema_migrations`; migrations 006 and 007 add GitHub Projects, linked GLPI ticket IDs, and the configured writable execution scope. Task content edits increment a revision; a saved triage report or run snapshot is tied to that revision. Task status changes must satisfy the domain transition graph. Tasks begin `pending`; triage routes incomplete context to `awaiting_context`, sufficient context to `awaiting_approval`, and explicit do-not-proceed recommendations to `blocked`. A task from the configured GitHub Project is queued immediately after its triage report is saved when its current scope matches that Project's configured writable scope. Local/manual tasks remain in `awaiting_approval`. Queueing snapshots task content, revision, project path, and canonical write scope transactionally. Only lifecycle commands may set `queued`, `running`, or `needs_reconciliation`. A completed run moves the task to `awaiting_review`; the user must still mark the current revision `completed`.

`github_project_sources` maps one local Orbyt project to an organization ProjectV2, a dynamically discovered single-select field/option, and a writable local execution scope. `source_connections` stores GLPI 10 API endpoints; all GitHub App and GLPI credentials are kept in the OS keyring. GitHub sync reads up to 10,000 Project items, then retains only open Issues assigned to the authenticated account and matching the configured Status option. It polls on startup and every five minutes while Orbyt is open, triaging at most three eligible pending tasks in each cycle. Each task preserves its local title, description, and workflow status during refresh. GitHub is read-only. GLPI is fetched only by a linked numeric ticket ID whose URL origin matches the configured GLPI endpoint. A context question is posted only after the user reviews and confirms the exact public follow-up. Disconnecting a source stops further reads but keeps imported task records; project deletion is blocked while a GLPI connection remains.

The global concurrency preference supplies the initial limit for new projects (three when unset); each project stores and uses its own limit thereafter. Project scopes are relative to the project root. Before claiming a queued run, the scheduler revalidates the task revision, project path, writable scope, and symlink boundary. It enforces the configured per-project active-run limit and serializes overlapping canonical write scopes; shared reads are not exclusive, though all current implementation runs acquire write locks. Locks stay persisted while a run is active or needs reconciliation.

## Supervised implementation execution

Local tasks are explicitly started from `awaiting_approval`. GitHub Project source setup explicitly chooses the writable scope used for sufficient-context auto-start. The scheduler claims runs transactionally, stores a write lock, and changes the run/task to `running` before launching OpenCode. A run uses the project root as its process and ACP session working directory so project configuration and context load consistently. Its prompt includes the task title, description, and relative scope as an instruction. The scope constrains scheduler conflict checks; it does not enforce filesystem access. The selected scope is an authorization boundary inside Orbyt's workflow, not an OS security boundary; OpenCode's effective tool permissions still govern tool actions and may allow them without another prompt.

Rust starts the configured executable as `opencode acp` without a shell and uses newline-delimited ACP v1 JSON-RPC over stdin/stdout. ACP creates a private child service; Orbyt does not open a network listener. The session uses the existing OpenCode installation/configuration and receives no extra client MCP servers. Progress, bounded assistant output, session ID, process ID, and permission state are persisted locally. The task title, description, and scope instruction go to the model provider configured in OpenCode.

ACP permission requests are surfaced only when OpenCode's effective policy asks for permission. The UI allows only the protocol's one-time allow or reject options; it never offers "always allow". Existing OpenCode rules, saved decisions, or plugins that allow an action remain effective and may let a tool run without an Orbyt prompt. The task approval therefore authorizes starting the run, but it does not override OpenCode's per-tool policy.

Cancel requests are sent to the ACP session. If ACP does not respond within 15 seconds, Orbyt begins process shutdown; it waits up to 5 seconds for a graceful exit before terminating the ACP parent. Because child tool processes may remain, a timeout or forced termination retains the scope lock and marks the run for reconciliation. A user must confirm that external OpenCode/tool work has stopped before reconciliation releases the lock. On application restart, persisted active runs move to `needs_reconciliation`; Orbyt does not resume or resend their prompt. Task, scope, project-path, and project-concurrency edits are blocked while runs remain queued or active; the active-run check and mutation are performed in one immediate transaction.

## OpenCode connection

The connectivity integration seam is the `verify_opencode` Tauri command. It invokes only the configured executable with the fixed arguments `api get /api/info`, optionally adding OpenCode's documented `--server` flag for a user-provided loopback endpoint. It has a 10-second timeout and caps stdout at 64 KiB; it does not pass prompts, shell input, or credentials. Default operation delegates service discovery/authentication to the local OpenCode CLI. Existing OpenCode configuration and credentials are not modified. The same optional endpoint is used by CLI API calls for session discovery and stateless triage; triage task text is therefore sent to the model provider configured on that service. Task implementation is a separate ACP subprocess path and does not receive the API endpoint override.

The optional service endpoint must be loopback HTTP, not arbitrary network input. Service/API failures are surfaced without dumping OpenCode stderr into the UI. Future OpenCode integrations must retain existing configuration, agents, commands, skills, MCP servers, and authentication.

The Sessions screen lists at most 100 existing sessions per registered project through the `session.list` OpenCode CLI operation and that project's canonical `directory` query parameter. Use the OpenAPI operation ID when passing query parameters: the generic `api GET /route` form in OpenCode 2.0.26 ignores `--param`. Stdout is capped at 1 MiB, session IDs and parent IDs are limited to 256 bytes without control characters, and titles are limited to 500 characters. The response's `data` envelope is decoded. This discovery screen stays read-only. Sessions started for Orbyt tasks are associated with persisted `task_runs` and shown in their task cards.

Task triage uses the OpenCode 2.0.26 `experimental.generate.text` operation (`POST /api/experimental/generate`). It uses the configured service's default model and has no project `location` parameter, so it receives task/source metadata and linked GLPI text, not project files; candidate paths are suggestions, not files inspected from disk. The Issue text, ticket text, public follow-ups, and bounded attachment metadata are sent to the model provider selected by the user's OpenCode configuration; attachment bytes are excluded. The operation is stateless and does not create a session or invoke tools. Stdout is capped at 64 KiB; output is untrusted, strictly deserialized, and validated before it can change task state. Reports are persisted transactionally with the resulting status transition. Failures move a still-triaging task to `failed`, which may be retried. On database open and each task-list query, triage states older than two minutes move to `failed` with a transition history entry, allowing the 60-second API call a grace period to finish normally. The task query refreshes every 30 seconds while the UI is active, so a restart before the grace period expires is reconciled later.

## Security and failure behavior

- Tauri commands validate IDs, names, priorities, directory existence, concurrency bounds, setting keys, URL constraints, and task transitions.
- SQLite enables foreign keys. Domain state transitions and transition-history insertion are performed transactionally.
- The frontend does not get unrestricted shell or filesystem APIs; directory selection uses the scoped Tauri dialog plugin.
- External task text is untrusted. Explicitly running triage sends the title and description to the configured OpenCode model provider; the prompt treats task data as untrusted and generated output is schema-validated.
- Approved task text and its scope instruction are sent to the configured OpenCode model provider when the run starts. ACP output and permission details are treated as untrusted and rendered as bounded text.
- An execution scope is not a security sandbox. Scope locks coordinate Orbyt runs but cannot prevent OpenCode or configured tools from accessing paths outside the scope.
- OpenCode's effective permission policy may allow tool actions without an ACP prompt. Orbyt does not silently rewrite that policy or promise a prompt for every action.
- GitHub and GLPI credentials are kept in the operating system credential store. Authenticated HTTP clients disable redirects, have a 20-second timeout and bounded response bodies, and never put credentials in URL parameters. GLPI endpoints require HTTPS except for loopback; GitHub uses the fixed official API host. Issue and GLPI text are untrusted and are sent to OpenCode during configured triage and any resulting implementation run. Attachment binaries are not included in triage.
- No Docker management, automatic service restart, worktree, source tree copy, or OS-enforced task sandbox is implemented.

## Future extension points

Future work can add GLPI image/file understanding, sync while Orbyt is closed, and stronger OS-enforced isolation. Additional source integrations should store provenance/references and keep credentials in OS secure storage rather than SQLite plaintext.
